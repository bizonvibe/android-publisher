# Каждый день в 12:00: R2 → Android → @crabscoder

Цель: компьютер Windows сам проверяет готовые дневные ролики в R2 и публикует новые **NORMAL_REEL** в `crabscoder`, без ежедневного ввода ключей, выбора элементов или подтверждения каждой публикации. Trial и автоматический перевод Trial не используются.

**Текущее ограничение:** код расписания и двух шагов отправки подготовлен и проверен с Mock Android. Он ещё не прошёл финальную публикацию на физическом TECNO. Нельзя объявлять ежедневный LIVE работающим до успешного локального теста. Компьютер и телефон не доступны из облака; расписание на вашем Windows удалённо не устанавливалось. Генерация в другом репозитории не изменялась.

## Как работает один ежедневный запуск

1. В 12:00 **Europe/Moscow** Windows Task Scheduler запускает локальный Python, в рабочем каталоге проекта и от вашего пользователя. Время задано явным UTC+03:00, а не зависит от часового пояса Windows.
2. Проверяются пять известных путей `reels/ru/daily/YYYY-MM-DD/01..05/manifest.json` за сегодня и вчера (подхват поздно завершившихся/пропущенных роликов). ListBucket не требуется. Общий batch-status не используется: в реальной партии он отставал от слотов.
3. Для существующего manifest проверяются `status=ready`, формат фабрики, prefix, точный video key, MIME, размер и SHA256. Отсутствие manifest означает «пока не готово»; AccessDenied и повреждённый manifest — ошибка, а не пустая очередь. Описание отдельно скачивается и проверяется.
4. Новые ролики обрабатываются последовательно. Сохраняются стабильные idempotency keys и SQLite-дедупликация по account/video ID/SHA256. Опубликованные и зарезервированные после неизвестного результата повторно не отправляются. Старые тестовые ролики вне дневного prefix не подхватываются.
5. Для каждого ролика проверяется аккаунт через профиль Instagram **перед импортом**, затем caption, режим, клавиатура скрывается автоматически. На экране компоновщика username может отсутствовать; для этого профиля используется ранее проверенный активный аккаунт. Телефоном параллельно не управляйте и аккаунт не переключайте.
6. Перед первым потенциально необратимым нажатием сохраняется SQLite barrier. **«Далее»** (`publish_next`) и финальная **«Поделиться»** (`publish`) — разные селекторы. Share нажимается только после появления отдельно настроенного `publication_confirmation`. Если после Next сразу появился маркер успеха, второе нажатие не делается. Если ожидаемое окно/результат не появился, исход UNKNOWN_RESULT, без повторной отправки.
7. Успех подтверждается явным UI-маркером текущей публикации. При капче/проверке личности/неизвестном результате — постоянная пауза всей очереди. При другом сбое текущий запуск останавливается. Скриншоты и stop.json сохраняются; сам обход защиты не выполняется.

По умолчанию `daily` — DRY_RUN, сохраняет первый найденный запрос в `data/daily-first-job.json`, оставляет подготовленным только один ролик и не накапливает открытые черновики. Для LIVE нужны одновременно ENV-разрешение, завершённая калибровка, успешный физический LIVE-тест с UI-проверкой и сохранённое одноразовое разрешение ежедневного режима. В последующих ежедневных запусках интерактивного ввода нет.

## Однократная настройка на телефоне

Сначала обновите ветку и зависимости:

```powershell
git pull --ff-only origin fix/first-android-reel
.\.venv\Scripts\python.exe -m pip install -e .
.\.venv\Scripts\python.exe -m android_publisher configure-daily-flow
```

Последняя команда мигрирует профиль на два шага, использует проверку аккаунта в начале, **сбрасывает старые publish-селекторы** и выключает прежнее разрешение LIVE. R2/USB/caption/normal marker остаются. По предыдущим дампам известно, что «Далее» открывает окно «Обновление оригинального аудио». Оно ещё не является успехом публикации.

Для выбора реального нового ролика выполните `daily` с R2 ENV (или DRY_RUN-обёртку после настройки ENV): он сохранит `data/daily-first-job.json`. Для партии 11 ноября можно указать `daily --date 2026-11-11 --lookback 0`. Затем используйте свежий интерактивный прогон:

```powershell
.\.venv\Scripts\python.exe -m android_publisher dry-run --job data/daily-first-job.json --mode NORMAL_REEL --interactive
```

Во время этого интерактивного DRY_RUN сохраните `publish_next` на кнопке «Далее» **в форме с описанием**, не на Next из редактора. Этот DRY_RUN останавливается до нажатия. Отдельной командой `calibrate --step ...` сохраняются селекторы:

| Имя | Что должно определяться |
| --- | --- |
| `publish_next` | Далее на форме с caption; только сохраняется при DRY_RUN |
| `publication_confirmation` | Однозначный заголовок/контейнер окна подтверждения, например «Обновление оригинального аудио» |
| `publish` | Финальная Share именно в этом окне; не Next и не «Выключить и поделиться» вместо другой политики аудио |
| `publication_success` | Явное подтверждение успешной загрузки текущего Reel; не профиль, не вкладка ленты и не кнопка Share |

Если окно «Обновление оригинального аудио» уже попадало в `data/jobs/.../hierarchy.xml`, повторно открывать его на тестовом ролике не требуется:

```powershell
.\.venv\Scripts\python.exe -m android_publisher import-confirmation
```

Команда находит сохранённый снимок и импортирует точные resource IDs заголовка (`clips_original_audio_nux_sheet_title`) и обычной кнопки Share (`clips_original_audio_nux_sheet_share_button`). Вариант `turn_off_and_share_button` не выбирается. `publish_next` сохраняется, прежнее разрешение автоматического LIVE сбрасывается. Телефон/ADB/R2 не используются. Для конкретного XML доступен `--xml путь`. Маркер `publication_success` этим снимком не подтверждается и должен настраиваться отдельно; старый DRY_RUN после изменения профиля для LIVE не подходит.

Калибровка не нажимает выбранные элементы и не публикует. Для финальных элементов нужен фактический экран телефона. Если UI не предоставляет надёжный маркер успеха, ежедневный LIVE **не включается**: нельзя заменить его произвольным заголовком или ручным owner-confirmed. В таком случае требуется отдельная доработка проверки результата по фактическому интерфейсу.

### Если сообщение успеха ещё неизвестно: один контролируемый пилот

Не нужно публиковать вручную ради настройки `publication_success`. После успешного свежего DRY_RUN нового NORMAL_REEL, сохранения `publish_next` и импорта двух final-селекторов можно явно выполнить один обучающий LIVE-пилот:

```powershell
powershell -ExecutionPolicy Bypass -File .\scripts\Run-DailyPublisher.ps1 -ExecutionMode LIVE -PilotDryRunId UUID_СВЕЖЕГО_DRY_RUN -LearnSuccess
```

Скрипт загружает R2 ENV пользователя, показывает интерактивный вывод (не прячет подтверждение в лог) и использует только указанный ролик. Требуется точная фраза `PUBLISH @crabscoder NORMAL_REEL` перед отправкой. Это **реальная публикация одного ролика**; пробная партия целиком не отправляется. Разрешение LIVE действует лишь в этом процессе, Task Scheduler остаётся DRY_RUN.

До отправки очищается кеш Android toast. После отправки до60сек проверяются новые явные сообщения о публикации в Instagram UI либо Android toast, например «Ваше видео Reels опубликовано» / «Your reel has been shared». Общие «Готово», «Загрузка», факт закрытия формы, произвольные тексты не принимаются. Канал toast недоступен — используется только явное подтверждение в иерархии UI. Если оба способа не дали подтверждения, результат UNKNOWN_RESULT, запись о попытке остаётся, очередь на паузе, повторного Share нет. `success-observations.jsonl` и скриншоты помогают разобрать причину без повторной отправки.

Только после наблюдавшегося явного подтверждения в профиль добавляется фактический selector либо точный текст toast, сохраняются прежний/новый hash профиля в результате PUBLISHED. Профиль помечается откалиброванным этим физическим тестом; ежедневное разрешение по-прежнему отдельно выключено. После этого используйте `enable-daily --pilot-job UUID_LIVE_ЗАДАНИЯ` и установщик с `-Live`, как ниже. `owner-confirmed` не подменяет автоматическую проверку.

Если прошло более30минут с DRY_RUN, сначала выполните новый `dry-run --job data/daily-first-job.json --mode NORMAL_REEL` и используйте его новый UUID. Не повторяйте пилот после отправки с неизвестным результатом: сначала проверьте телефон/записи.

Ниже остаётся альтернативный путь, когда UI-маркер успеха уже известен и откалиброван заранее.

Когда все четыре селектора проверены, `approve-profile` запрашивает `APPROVE @crabscoder`. Затем повторите `dry-run --job data/daily-first-job.json --mode NORMAL_REEL --interactive` (он создаёт новый прогон и фиксирует окончательный хеш профиля; старый daily DRY_RUN после изменения профиля использовать нельзя), и один локальный `live --from-dry-run UUID` с явным `PUBLISHER_ALLOW_LIVE=true`. В этом разовом тесте перед отправкой показываются account/caption/mode/SHA256 и требуется точная фраза владельца. Должен получиться **PUBLISHED** с `verification=ui-success-marker`. Это реальная публикация одного ролика, а не тестовая заглушка; этот же файл daily повторно не опубликует.

После успешного теста:

```powershell
.\.venv\Scripts\python.exe -m android_publisher enable-daily --pilot-job UUID_УСПЕШНОГО_LIVE_ТЕСТА
```

Введите `ENABLE DAILY @crabscoder`. Сохраняется разрешение именно на `crabscoder`, NORMAL_REEL, этот телефон, Instagram version и точный профиль. Изменение телефона/app/profile блокирует daily до новой проверки. Никакие секреты в разрешение не записываются.

## Установка Windows Task Scheduler

Пока профиль не испытан, можно установить только ежедневный **DRY_RUN**:

```powershell
powershell -ExecutionPolicy Bypass -File .\scripts\Install-DailyPublisher.ps1
```

Для реального ежедневного режима **после успешного теста и enable-daily**:

```powershell
powershell -ExecutionPolicy Bypass -File .\scripts\Install-DailyPublisher.ps1 -Live
```

Установщик один раз спросит R2 Access Key ID/Secret скрытым вводом и сохранит их **в пользовательских переменных окружения Windows**, чтобы запуск в 12:00 не ожидал клавиатуру. Значения не записываются в task XML/CLI arguments/JSON проекта. Этот Windows-пользователь имеет доступ к своим ENV; защищайте его учётную запись. Endpoint/bucket/serial берутся из `publisher.local.json`. Код задачи обновляет ENV из пользовательских bindings при каждом старте, даже если служба планировщика получила старое окружение.

Задача называется `Crabscoder Android Reels Publisher`. Первый запуск — ближайшие **будущие** 12:00 Москвы, не немедленная публикация при установке. Один запуск за раз; есть OS-lock телефона и SQLite. Требуется: Windows включён, пользователь вошёл, интернет работает, телефон разблокирован, заряжается/подключён USB, Instagram авторизован. PIN/биометрия/капча не обходятся. При пропущенном времени Windows использует StartWhenAvailable; если при реальном запуске USB недоступен, публикации не будет. Следующий дневной запуск проверяет также вчерашние слоты. Для более старого пропуска можно явно использовать `--date YYYY-MM-DD` либо `--lookback N` (максимум7).

Для теста без регистрации системной задачи: `Install-DailyPublisher.ps1 -Preview` только выводит XML, не спрашивает ключи и ничего не устанавливает. Удаление расписания:

```powershell
Unregister-ScheduledTask -TaskName 'Crabscoder Android Reels Publisher' -Confirm:$false
```

## Разовый запуск той же автоматизации

С уже настроенными ENV и профилем:

```powershell
# Только подготовка первого нового ролика:
.\.venv\Scripts\python.exe -m android_publisher daily
# Реальная последовательная публикация новых файлов, только с разрешённой политикой:
.\.venv\Scripts\python.exe -m android_publisher daily --live
```

Второй вариант требует `PUBLISHER_ALLOW_LIVE=true` даже при сохранённой политике. В Task Scheduler его выставляет процесс запуска лишь при явно установленном `-Live` режиме. Наличие сохранённой политики само по себе не включает LIVE в обычном терминале/API.

Логи: `data/schedule-logs/*.log`; последний отчёт: `data/daily-last-run.json`; результаты/дедупликация: SQLite; подробности каждого задания: `data/jobs/UUID/`. Если результат UNKNOWN_RESULT, не повторяйте Share вручную и не удаляйте базу. Проверьте профиль и после выяснения причины снимите паузу через `resume`; старое задание не отправляется заново.

Новая генерация или расписание генератора в этом изменении не запускались/не менялись. Если генератор готовит файлы к10:00, задача в12:00 читает то, что реально завершено. Незавершённые слоты не считаются опубликованными.
